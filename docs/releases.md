# Plugin releases and verification

## Jenkins-hosted releases

The canonical repository is [jenkinsci/awarely-scan-plugin](https://github.com/jenkinsci/awarely-scan-plugin). The first official release, **18.v7f17b_86cf4b_8**, is [published in the Jenkins artifact repository](https://repo.jenkins-ci.org/releases/io/jenkins/plugins/awarely-scan/18.v7f17b_86cf4b_8/). The release is listed in the [Jenkins Update Center](https://plugins.jenkins.io/awarely-scan/). Jenkins-hosted releases use versions such as `123.vabcdef456789`, generated by the official release workflow. They keep plugin ID `awarely-scan` and update earlier manually installed versions.

Install from **Manage Jenkins → Plugins → Available plugins → Awarely Scan** for a new installation; use **Plugins → Updates** for an existing installation. Jenkins obtains plugins and checksums through its Update Center. The [plugin page](https://plugins.jenkins.io/awarely-scan/) and [official releases](https://github.com/jenkinsci/awarely-scan-plugin/releases) identify published versions. An Incrementals build is a development artifact, not an Update Center release. Validate upgrades on staging and retain a controller backup.

CLI **v0.12.0** and managed Syft **1.54.1** remain pinned. Jenkins-hosted HPI releases use Jenkins publication infrastructure; the historical GitHub Sigstore command below applies only to the original GitHub-built assets.

## Official installation smoke test

On 2026-10-17, an isolated Jenkins 2.580.1 / JDK 21 controller upgraded the manually installed 0.2.0 plugin to **18.v7f17b_86cf4b_8** through Jenkins Update Center. Signed metadata verification remained enabled. The installed HPI SHA-256 matched `a732c60795611d61d41d1ec491b9a4ab07cc5b8638cc211bb671c57b72d2038e`.

The plugin loaded without failures after restart, preserved all existing Awarely global settings, and retained a newly saved job approval and Pipeline configuration through a second restart. On a non-root Linux amd64 agent, the published plugin ran CLI v0.12.0, collected an npm lockfile, completed Check against an isolated Monitor staging API, and exposed its report and archived JSON artifacts. An affected synthetic fixture returned one version-confirmed match; its remediated control returned zero matches and zero unevaluated components. Credential tokens were absent from both build logs.

This verifies the official upgrade path and a scan/Check workflow. The catalog used synthetic acceptance data; this is not a fresh-controller dependency installation test or a repeat of every collector/security test.

## Manual installation of the current Jenkins release

Prefer Plugin Manager. For an administrator-managed manual installation, download the official HPI and its SHA-256 from the [Jenkins Maven release directory](https://repo.jenkins-ci.org/releases/io/jenkins/plugins/awarely-scan/18.v7f17b_86cf4b_8/), using a new empty directory:

```sh
curl --fail --location --proto '=https' --proto-redir '=https' \
  'https://repo.jenkins-ci.org/releases/io/jenkins/plugins/awarely-scan/18.v7f17b_86cf4b_8/awarely-scan-18.v7f17b_86cf4b_8.hpi' \
  -o awarely-scan-18.v7f17b_86cf4b_8.hpi
curl --fail --location --proto '=https' --proto-redir '=https' \
  'https://repo.jenkins-ci.org/releases/io/jenkins/plugins/awarely-scan/18.v7f17b_86cf4b_8/awarely-scan-18.v7f17b_86cf4b_8.hpi.sha256' \
  -o awarely-scan-18.v7f17b_86cf4b_8.hpi.sha256
sha256sum awarely-scan-18.v7f17b_86cf4b_8.hpi
cat awarely-scan-18.v7f17b_86cf4b_8.hpi.sha256
```

The two SHA-256 values must be identical; stop if either download fails or they differ. On macOS use `shasum -a 256` instead of `sha256sum`. These are official Jenkins repository artifacts/checksums, not the historical GitHub Sigstore bundles below. Install the required dependencies and upload the HPI as described in the [walkthrough](how-to.md#1-prepare-jenkins-once). Keep a controller backup and validate on staging before production.

## Preserved GitHub releases

The six historical releases from **0.1.0-alpha.2** through **0.2.0** are mirrored in the canonical repository with byte-for-byte identical assets, original tags and checksums. Their release notes identify their original publication dates and build identity. The original repository remains available as a historical archive to preserve existing links and review history. Mirroring a release does not rebuild or re-sign it, and does not publish it to the Jenkins Update Center.

The last historical stable GitHub release is **0.2.0**. It lacks the later hosting-review fixes; prefer the Jenkins-hosted release.

Download these four files from the [preserved v0.2.0 release](https://github.com/jenkinsci/awarely-scan-plugin/releases/tag/v0.2.0) into a new empty directory:

- `awarely-scan-jenkins-0.2.0.hpi`
- `awarely-scan-jenkins-0.2.0.hpi.sigstore.jsonl`
- `awarely-scan-jenkins-0.2.0.cdx.json`
- `SHA256SUMS`

Before installing historical controller code, run this in that directory with an up-to-date GitHub CLI. Keep the original `awarelyeu` repository and workflow identity even when downloading the mirrored assets from `jenkinsci`:

```sh
gh attestation verify awarely-scan-jenkins-0.2.0.hpi \
  --bundle awarely-scan-jenkins-0.2.0.hpi.sigstore.jsonl \
  --repo awarelyeu/awarely-scan-plugin \
  --signer-workflow awarelyeu/awarely-scan-plugin/.github/workflows/preview-release.yml \
  --source-ref refs/tags/v0.2.0 \
  --deny-self-hosted-runners
sha256sum --check SHA256SUMS
```

On macOS, replace the last command with `shasum -a 256 -c SHA256SUMS`. Public bundles do not require a GitHub account; trust-root updates still need internet access. Stop if provenance or digests fail. If `gh` is unavailable, follow the official [GitHub CLI installation guide](https://github.com/cli/cli#installation); it is a verifier for this administrator step, not a scanner runtime dependency.

The public attestation covers the HPI, dependency inventory and checksum list. Separate bundle files are provided for each subject; the bundle downloaded above also lets you authenticate the SBOM by repeating `gh attestation verify` with the `.cdx.json` file and the same policy flags. The attestation identifies the build source, not a guarantee that code has no vulnerabilities.

After verification, follow the [English](how-to.md) or [Romanian](how-to.ro.md) installation guide. Jenkins keeps the plugin ID `awarely-scan`, so this HPI updates an installation of the previous preview. Keep a controller backup and test on staging first.

The CycloneDX inventory includes provided Jenkins/plugin dependencies, not only JARs embedded in the HPI. The HPI carries Maven license metadata; this plugin is Apache-2.0 and its dependencies retain their own licenses.

## Historical publication procedure before Jenkins hosting

1. Authenticate CLI pins with `python3 scripts/pin-cli.py --check`. To deliberately update them, use `python3 scripts/pin-cli.py --version vVERSION` and review the resulting change. The CLI remains in the scanner repository.
2. Review source, both walkthroughs, release notes and publication changes through a PR. Require Linux amd64/arm64 build checks, packaging guard tests, secret scanning and Jenkins Security Scan. Runtime changes need appropriate Pipeline/Freestyle acceptance tests on isolated agents.
3. After merge, create a new `vX.Y.Z` stable tag or `vX.Y.Z-alpha.N` preview tag at the reviewed, GitHub-verified commit on `main`. Use a lightweight tag on that signed commit, or a signed annotated tag that GitHub verifies. Unsigned annotated tags are refused. Never reuse a version or move an existing tag.
4. `.github/workflows/preview-release.yml` runs only in `awarelyeu/awarely-scan-plugin`. It runs the build matrix, verifies the tag target, commit signature and membership in `main`, authenticates CLI pins, builds with explicit `changelist` and `scmTag` values, and checks the packaged HPI, SBOM and embedded pins before attesting and publishing a new GitHub release. Stable tags become Latest; alpha tags remain prereleases.
5. Download the published assets and verify provenance and checksums against that exact repository, workflow and tag before staging the HPI. Publication fails if the release already exists; fix a defective published artifact with a new version rather than replacement.

The POM and `.mvn/` retain Jenkins's standard changelist/Incrementals configuration. Only the GitHub release build supplies an explicit version; ordinary local builds remain snapshots.

## Maintainers: Jenkins-hosted releases

Jenkins-hosted releases use the official Maven/CD workflow, which feeds Jenkins update sites. Complete [hosting approval and CD activation](hosting.md) first. The prepared `cd.yml` is manual, disabled outside the canonical Jenkins repository, and defaults to validation only. Hosting/CD approval and Jenkins-provisioned Maven credentials are in place. Run validation first and require successful Jenkins CI for the exact default-branch commit before publishing. A stable or preview GitHub release does not publish to any Jenkins update site.

After hosting, use Jenkins Incrementals for development previews and official CD for releases. The pre-hosting GitHub release workflow is restricted to the Awarely repository and will not publish from `jenkinsci`.
